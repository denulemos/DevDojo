### IA vs LLM

La IA es el universo completo: todo sistema que intenta simular el razonamiento humano (sistemas de recomendación, reconocimiento de voz, etc.). 

Un LLM es un tipo específico de modelo de lenguaje entrenado con grandes cantidades de texto para generar texto coherente y relevante. 

Los LLM son las "estrellas" de la IA, pero no son la IA completa. Se usan como sinónimos erróneamente.

### Como funciona la IA?

Son sistemas que toman decisiones automatizadas para maximizar un objetivo asignado. Necesitan 4 elementos:

- Posibles acciones entre las que elegir
- Un objetivo a maximizar
- Conocimientos básicos
- Conjuntos de datos para el entrenamiento

El aprendizaje automático detecta patrones en grandes cantidades de datos en lugar de seguir instrucciones codificadas manualmente.

Los 3 pilares que hicieron posibles los LLM actuales justamente fueron: 

1. Muchos datos para el entrenamiento de modelos
2. Mayor poder computacional
3. Nuevas técnicas de entrenamiento

#### Exploracion vs Explotacion

La explotación es usar técnicas ya probadas que funcionan, mientras que la exploración es arriesgarse a probar algo nuevo con la posibilidad de encontrar mejores opciones. 

Los sistemas de IA navegan esta tensión siguiendo el principio de optimismo ante la incertidumbre: optan por la opción con mayor potencial de recompensa, incluso si es incierta o arriesgada.

#### ¿Por qué se dice que la IA es una máquina de probabilidades?

Porque siempre existe la posibilidad de que genere una respuesta incorrecta o inexacta, incluso ante el mismo input repetido. La IA aprende a través de patrones en los datos, no a través de la comprensión del mundo real, por lo que puede generar respuestas que parecen coherentes pero son completamente falsas.

### ¿Cuáles son los 4 componentes principales de un agente?

- **Models**: Para razonar, planificar y generar respuestas (puede usar más de uno)
- **Tools**: Para recuperar datos y realizar acciones mediante APIs o servicios
- **Orchestration**: El cerebro; configura pasos, lógica, memoria y estado
- **Runtime**: Ejecuta el sistema cuando recibe una pregunta del usuario

### Multi-agent vs Single-agent

- **Multi-agent**: Cuando hay tareas complejas que requieren distintos tipos de conocimiento y herramientas, y se pueden dividir en sub-tareas independientes. Cada agente puede especializarse en un área y colaborar con otros agentes para resolver la tarea completa.
- **Single-agent**: Cuando la tarea es simple y puede ser resuelta por un solo agente con un conjunto limitado de herramientas y conocimientos.

## **Tokens**

Son fragmentos de texto que un modelo de lenguaje utiliza como unidad básica para leer, interpretar y generar contenido. El modelo piensa en tokens, no en palabras. Por ejemplo, "Me gusta programar" puede separarse en "Me", "gusta", "program" y "ar". Cada token puede ser una palabra entera, parte de una palabra, un espacio o un símbolo.

- Determinan cuánto texto puede procesar el modelo a la vez
- Afectan el costo de uso de las APIs
- Influyen en la longitud máxima de entrada y salida
- Cuantos más tokens, más trabajo debe realizar el modelo

### ¿Qué tipos de tokens existen?

- **Input tokens**: Los enviados al modelo
- **Output tokens**: Los que el modelo responde
- **Context Window**: La cantidad máxima de tokens que el modelo puede manejar en una interacción

## **Temperatura**

Es un valor decimal entre 0 y 1 que controla el nivel de aleatoriedad en las respuestas. 

Una temperatura baja (cercana a 0) hace al modelo más determinista y repetitivo, recomendada para análisis de información. 

Una temperatura alta (cercana a 1) aumenta la creatividad y diversidad, recomendada para escritura creativa. 

Importante: la temperatura no asegura respuestas distintas ante cada intento, sino que controla el nivel de aleatoriedad.

## **Contexto**

Es la información adicional que se le proporciona al modelo para ayudarlo a generar respuestas más relevantes y precisas.

Incluye información sobre el tema, el tono deseado, o cualquier detalle útil.

## **IA Generativa**

Es un sistema que, además de analizar datos para tomar decisiones, crea contenido nuevo como imágenes, vídeos, texto, etc. Aprende en 2 etapas:

- **Pre-training**: Analizar patrones a lo largo de millones de ejemplos
- **Fine-tuning**: Ajustar el modelo para tareas específicas

## **Alucinaciones**

Son secuencias de palabras que parecen tener sentido pero no tienen base en la realidad. 

Es información inventada. 

Se ven frecuentemente con tópicos de noticias recientes, donde la IA no tiene acceso a esa información e intenta adivinar, generando respuestas falsas

## **Sesgo o Bias**

Los LLM se alimentan de información de personas diversas, pero a veces generan información que refleja un sesgo social. Se representa el punto de vista dominante. 

Por ejemplo, si se pide generar una imagen de un doctor y una enfermera, frecuentemente genera un doctor hombre y una enfermera mujer, especialmente en la IA Generativa de imágenes. 

Esto refleja un sesgo de género en la sociedad, no un error del modelo.

## **Exceso de complacencia**

Los LLM intentan ser extremadamente complacientes, dando la razón al usuario en cosas que no necesariamente son correctas. 

Fueron entrenados con texto de internet donde la gente suele ser complaciente. Esto significa que validan ideas y creencias que pueden ser incorrectas.

## **Coding Assistant**

Es un sistema que utiliza LLM para resolver tareas complejas de código. Cuando recibe una task, toma 3 pasos:

- **Recoger contexto**: Reconocer el error y qué archivos están involucrados
- **Armar un plan**: Decidir cómo resolver el error
- **Tomar acción**: Implementar el cambio y correr comandos necesarios

Los pasos 1 y 3 requieren **Tool Use**, ya que un LLM por sí solo no puede leer código ni correr comandos.

## **Tool Use**

Es la capacidad de un LLM de usar herramientas externas para completar tareas. 

Funciona mediante instrucciones "under the hood" como "If you want to read a file, respond with 'ReadFile: name of file'".

No todos los LLM son buenos en Tool Use. 

Las herramientas pueden:

- Combinarse para tareas complejas
- Ser extensibles (agregar nuevas herramientas como acceso a BD o APIs)
- Acceder al código fuente sin necesidad de indexarlo

### ¿Qué son las Tool Functions y qué requisitos deben cumplir?

Son funciones Python ejecutadas cuando el agente decide que necesita información extra. Deben:

- Usar nombres descriptivos, incluyendo los parámetros
- Validar inputs correctamente y devolver errores claros
- Los mensajes de error deben ser explicativos para que el agente pueda entenderlos y corregirse

### ¿Cómo se define un JSON Schema para que el LLM entienda una Tool Function?

Se crea un objeto JSON con:

- `name`: Nombre de la función (usado para invocarla)
- `description`: Descripción clara de lo que hace
- `input_schema`: Esquema JSON que describe los parámetros de entrada, su tipo, descripción y si son requeridos

### ¿Qué estructura tiene un ToolResult?

- `tool_use_id`: Identificador único que debe coincidir con el bloque ToolUse correspondiente
- `content`: El output de la función, serializado como string
- `is_error`: Booleano que indica si ocurrió un error durante la ejecución

### Multi-Turn Tool Use - Conversation Loop

Es cuando una sola request requiere que el LLM llame a tools de manera consecutiva. 

Por ejemplo, ante "¿Qué día será en 103 días?", el LLM:

- Llama a `get_current_datetime` para obtener la fecha actual
- Recibe el resultado
- Llama a `add_days_to_date` con la fecha y 103 días
- Recibe el resultado
- Responde al usuario

Se implementa con un loop que continúa hasta que el `stop_reason` (Que es porque el LLM ha terminado de usar herramientas) del LLM no sea `tool_use`

### ¿Cómo se manejan errores en el Tool Use (Fine-grained tool calling)?

Puede suceder que una tool devuelva respuestas no válidas como un undefined inesperado. 

Se manejan con `try-catch` sobre el JSON parsing. 

Se recomienda implementar esto cuando:

- Se necesita mostrar progreso en tiempo real
- Se quiere procesar resultados parciales rápidamente
- Los retrasos de buffering afectan la experiencia de usuario
- Se tiene implementado un manejo robusto de errores JSON

## **RAG (Retrieval-Augmented Generation)**

Es una técnica para trabajar con documentos grandes que superan la capacidad de una prompt. 

RAG separa los documentos en chunks y solo toma las partes necesarias para resolver una request. 

Es necesario porque las prompts largas son más costosas y lentas.

- **Indexación**: El documento se divide en chunks y se indexa
- **Recuperación**: Se recuperan los chunks relevantes usando técnicas de búsqueda
- **Generación**: El modelo genera una respuesta basada en la información recuperada

Requiere preprocesamiento del documento. No es una solución simple, pero es escalable y eficiente.

1. Se recibe un texto y una pregunta
2. Se separa el texto en chunks
3. Se generan los embeddings de cada chunk
4. Se guardan en una base de datos vectorial
5. Se procesa la pregunta del usuario por el mismo pipeline de embedding
6. La base de datos busca los chunks más relevantes mediante el algoritmo de coseno
7. Se construye y devuelve el prompt final

### Estrategias de chunking

- **Size-based chunking**: Divide el texto en chunks de tamaño fijo. Simple pero puede cortar frases. Se agregan caracteres de overlap para contexto. Funciona en cualquier tipo de texto, incluido código.
- **Structured-based chunking**: Divide según la estructura del texto (párrafos, oraciones). Útil cuando controlamos y conocemos el formato del documento.
- **Semantic-based chunking**: Divide según significado semántico, usando separadores jerárquicos. Es el más inteligente pero puede fallar con términos específicos.

### BM25

BM25 (Best Match 25) es un algoritmo que combina búsqueda semántica con búsqueda léxica. 

Funciona así:

- Divide la pregunta en términos individuales
- Cuenta la frecuencia de cada término en el documento
- Pondera los términos (los raros/específicos pesan más)
- Devuelve documentos con más instancias de términos de alta ponderación

Es eficaz porque da mayor importancia a términos raros y específicos, ignora palabras comunes, y funciona bien para términos técnicos e identificadores.

### Text Embeddings

Son representaciones vectoriales (listas de números) de cada chunk de texto. 

Después de separar el documento, se transforma cada chunk en un vector para poder comparar con el vector de la pregunta del usuario. 

El chunk con el vector más cercano es el más relevante. Cada número representa un score respecto al texto, y su significado depende de cómo fue entrenado el modelo.


## **AI Fluency**

### ¿Cuáles son las 3 formas en que las personas se involucran con la IA?

- Automatización: La IA completa tareas basadas en tus instrucciones
- Augmentation: La IA funciona como un compañero con el cual planificas en conjunto
- Agency: La IA toma decisiones por sí misma basadas en tus instrucciones

### 4Ds de la IA

- Delegation: Decidir qué trabajo hacer tú y qué dejarle a la IA
- Descripción: Comunicación clara con los sistemas de IA
- Discernimiento: Evaluar la respuesta de la IA con ojo crítico
- Diligencia: Asegurarse de que las interacciones con la IA sean responsables

### Delegar correctamente a la IA

- Conocer el problema: entender metas y tareas
- Conocer los distintos sistemas de IA y sus capacidades
- Delegar de manera correcta con instrucciones claras y específicas

La meta no es automatizar el 100%, sino encontrar el equilibrio adecuado

### ¿Qué comprende la Descripción como capacidad de AI Fluency?

Es el arte de comunicarse efectivamente con la IA. Se compone de:

- Descripción del producto: Qué se necesita que cree la IA
- Descripción del proceso: El flujo que debe seguir para construirlo
- Descripción de la Performance: Cómo debe comportarse la IA (tono, si debe hacer preguntas de aclaración, etc.)

### ¿Qué tipos de discernimiento existen?

- Discernimiento de Producto: Evaluar la calidad del output
- Discernimiento del Proceso: Evaluar cómo la IA abarcó la tarea
- Discernimiento de Performance: Evaluar cómo cumplió con objetivos y estilo de comunicación

### ¿Qué tipos de diligencia existen?

- Diligencia de Creación: Qué sistemas de IA se eligen y cómo se trabaja con ellos
- Diligencia de Transparencia: Ser abierto respecto al rol de la IA en tu trabajo
- Diligencia de Deployment: Asumir responsabilidad por los resultados de la IA que se comparten con otros

## **Prompt Engineering**

Es un conjunto de técnicas para diseñar y perfeccionar prompts de manera que los modelos generen respuestas óptimas. Involucra un proceso iterativo:

- Setear una meta
- Crear el primer prompt (draft)
- Evaluar el prompt
- Aplicar técnicas de mejora
- Re-evaluar los resultados

### Principios de prompting efectivo

- Setear el escenario: Definir rol, contexto y objetivos
- Dar contexto: Ser claro sobre qué se precisa, por qué y cómo
- Definir la tarea: Qué acción específica tomar
- Dar ejemplos (Few-shot prompting): Mostrar formatos esperados
- Especificar constantes y reglas: Formato, límites, especificaciones
- Separar en pasos lógicos: Dividir tareas complejas en pasos
- Permitir que la IA piense primero: Darle espacio para razonar
- Definir el tono: Formal, casual, conciso, etc.

### ¿Cómo se resuelven problemas comunes en prompts?

| Problema | Solución |
| :-- | :-- |
| Respuesta muy genérica | Aportar más contexto y detalles |
| Respuesta muy corta o larga | Especificar longitud explícitamente |
| Sin formato | Usar instrucciones de formato claras o etiquetas XML |
| Información errónea (alucinación) | Pedir citas de fuentes o razonamiento paso a paso |
| Tono incorrecto | Ajustar el tono explícitamente en el prompt |

Si una conversación larga tomó mal rumbo, es más eficiente iniciar una nueva con un prompt refinado.

### ¿Por qué es importante ser específico en los prompts?

Porque evita que el agente interprete libremente. Se puede:

- Listar qué debe y qué no debe tener el output (largo, formato, elementos, tono)
- Listar el camino de razonamiento que debe seguir (especialmente para soluciones complejas o múltiples puntos de vista)
- Combinar ambas técnicas para obtener mejores resultados

### ¿Para qué sirve la estructura XML en prompts?

Cuando se envía información específica, las etiquetas XML ayudan a la IA a entender la estructura deseada. No hay etiquetas predefinidas; se crean las necesarias. Ejemplo: `<meal_history>`, `<athlete_information>`, `<code>`. Esto es útil para separar diferentes tipos de información dentro de un mismo prompt

### One-shot y Multi-shot prompting

- One-shot: Dar un solo ejemplo del formato deseado para que la IA lo entienda
- Multi-shot: Dar varios ejemplos para cubrir distintos escenarios

Ambas técnicas ayudan a la IA a entender exactamente el tipo de output esperado.

### ¿Cómo se pueden controlar outputs que deben cumplir restricciones numéricas (como caracteres máximos)?

Los números son mejores que las palabras ("máximo 70 caracteres" es mejor que "mantener los commits cortos"). También se puede usar maxLength en el strict schema. Sin embargo, sigue siendo probabilístico: no es 100% seguro, pero es mucho más probable que se cumpla

## **Prompt Evaluation**

Es la medición automática de la efectividad de los prompts mediante:

- Testing de respuesta esperada vs recibida
- Comparación de versiones del mismo prompt
- Revisión de outputs en busca de errores

Se usan Evaluation Pipelines para automatizar el proceso e iterar rápidamente.

### Ciclo de evaluación de prompts

1. Escribir un prompt en draft
2. Crear un dataset de evaluación
3. Evaluar el prompt con el dataset
4. Analizar resultados con un Grader (puntuación 1-10)
5. Mejorar el prompt
6. Repetir si es necesario

### Graders

- Grader Humano: Un humano evalúa y puntúa la respuesta
- Code Grader: Evaluación programática (sintaxis, si el código corre, etc.)
- Model Grader: Otro modelo de lenguaje evalúa la calidad de la respuesta

¿Qué formato quiero? → Code Grader (output estructurado)
¿Qué sintaxis es válida? → Code Grader (corrección sintáctica)
¿Cómo se ejecutó la tarea? → Model Grader (relevancia y coherencia)

### Evaluation Pipeline

1. Se crea un dataset JSON con tareas
2. Se combina el prompt con cada tarea del dataset
3. Se obtiene el output del modelo para cada tarea
4. Se evalúa cada output con un Grader
5. Se obtienen scores y se identifican áreas de mejora
6. Se refina el prompt y se repite

Se recomienda usar Haiku para la evaluación por ser más veloz y controlar la concurrencia para evitar errores de cuota.

## **Claude**

Claude es un LLM desarrollado por Anthropic, empresa fundada por ex empleados de OpenAI. Se lanzó en marzo de 2023. Fue construido bajo el enfoque de Constitutional AI para ser honesto, seguro y útil. Se describe como un asistente de IA para tareas complejas (código, emails, etc.), no solo un chatbot.

- Claude Opus: Pensamiento complejo y arquitectura
- Claude Sonnet: Daily coding, el más balanceado entre costo y performance
- Claude Haiku: Tareas simples y cotidianas, cost effective

### Projects

Son workspaces con su propia memoria, historial de chat y base de datos con instrucciones personalizadas. Incluyen:

- Project Knowledge: Base de datos con documentos
- Project Instructions: Guían el comportamiento de Claude
- RAG automático: Se habilita cuando la knowledge base alcanza cierto límite
- Permisos: Owner (control total), Editor (edita, no gestiona miembros), Viewer (solo lectura)

### Skills

Son carpetas de instrucciones, scripts y recursos que Claude carga dinámicamente. Tipos:

- Anthropic Skills: Generales, mantenidas por Anthropic
- Custom Skills: Creadas por usuarios
- Diferencia con Project Instructions: Los proyectos guardan conocimiento, las skills guardan y realizan procesos

### Connectors y MCP

Los Connectors permiten a Claude acceder a herramientas externas (Web, Desktop). Se implementan a través del estándar abierto MCP (Model Context Protocol), un protocolo que permite a los modelos acceder a herramientas y fuentes de datos externas de manera segura y estandarizada.

### Hooks

Permiten conectar a Claude con herramientas de desarrollo (PreToolUse y PostToolUse). Se configuran en:

- Global: `~/.claude/settings.json`
- Project: `.claude/settings.json`
- Project (no committed): `.claude/settings.local.json`

### Plan Mode y Thinking Mode

- Plan Mode: Pensamiento estructurado para tareas por pasos
- Thinking Mode: Pensamiento fluido y creativo

### ¿Cuál es el flujo de una request a la API de Claude?

1. Request al servidor
2. Request a Anthropic API
3. Procesamiento en el Modelo
4. Response al servidor
5. Response al cliente

### ¿Por qué las requests a la API de Anthropic deben hacerse desde un servidor y no desde el cliente?

Porque se requiere una API Key secreta para autenticar al usuario. Esta key NO debe exponerse en el código del cliente por seguridad.

### ¿Qué campos requiere una request a la API de Claude?

- API Key
- Model: El modelo a utilizar (ej. claude-3-sonnet)
- Messages: El mensaje del usuario
- Max Tokens: El límite de tokens que puede generar

### ¿Cuáles son los 4 pasos del procesamiento de una request en Claude?

1. Tokenización: Separar el mensaje en tokens
2. Embedding: Convertir cada token en una lista de números que representan sus posibles significados
3. Contextualización: Refinar cada embedding según el contexto
4. Generación: Calcular probabilidades para cada siguiente palabra, usando combinación de probabilidad y aleatoriedad controlada; repetir hasta terminar

La generación se detiene cuando se alcanza el máximo de tokens, termina la oración (EOS), o algo detiene la ejecución.

### ¿Qué incluye la respuesta de la API de Claude?

- Message: El texto generado
- Usage: Cantidad de input y output tokens usados
- Stop Reason: Razón de detención ("max_tokens", "eos", "stop_sequence", etc.)

### ¿Cómo se configura el entorno para usar la API de Claude?

1. Obtener una API Key
2. Instalar Jupyter Notebook
3. Instalar dependencias: `anthropic` y `python-dotenv`
4. Crear archivo `.env` con `ANTHROPIC_API_KEY`
5. Crear el API Client con `Anthropic()`

### ¿Cómo funcionan las conversaciones multi-turno con la API de Claude?

La API es stateless (sin estado): no almacena historial de mensajes. Para que Claude recuerde el contexto, el cliente debe almacenar y enviar todo el historial alternando roles user y assistant en el array de messages

### System Prompts

Son una forma de personalizar la interacción. Por ejemplo, si el chatbot es un asistente de cocina, el System Prompt le dice a Claude que responda como chef profesional. Se envían con la propiedad system en la request de messages

### Response Streaming

Una respuesta completa puede tardar 10-30 segundos. En lugar de esperar, el streaming muestra chunks de respuesta en tiempo real. Tipos de eventos:

- `MessageStart`: Nuevo mensaje siendo enviado
- `ContentBlockStart`: Nuevo bloque de contenido
- `ContentBlockDelta`: Chunks del texto actual (se reciben varios)
- `ContentBlockStop`: Bloque terminado
- `MessageDelta`: Mensaje completo
- `MessageStop`: Fin de la información

Se habilita con la propiedad `stream=True`.

### Extended Thinking

Permite al modelo "pensar" antes de responder ante problemas complejos. La respuesta tiene dos partes:

- Thinking: El razonamiento del modelo (no se muestra al usuario)
- Response: La respuesta final
- Signature: Identificador para asegurar que los bloques no fueron modificados

- Beneficios: Mejor razonamiento, mayor accuracy, transparencia.
- Desventajas: Mayor costo (thinking tokens), mayor latencia, mayor complejidad.

Si se recibe un Redacted Thinking block, significa que el modelo encontró contenido de alta peligrosidad en su pensamiento; se recomienda revisar el prompt

### Fork Sessions

Son copias de una sesión de conversación que se pueden compartir con colegas. Se pasa el `session_id` y el colega lo usa para crear un Fork Session. Con `--restore`, la conversación puede resumirse sin recargar toda la información
